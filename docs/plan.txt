PS-05 — Agentic Paper Trading Engine
1. Vision
Build a production-grade paper trading platform that simulates an Indian equity exchange environment using live market data while maintaining exchange-like order execution, realistic market-depth fills, margin validation, charges, positions, P&L and complete financial traceability.
On top of this deterministic trading engine, build an Agentic Trading Intelligence Layer capable of performing market research, news analysis, portfolio analysis, stock discovery, event monitoring, risk explanations, personalized insights and trade recommendations.
The system should behave like two separate systems:
                   ┌─────────────────────────────────────┐
                    │       AGENTIC INTELLIGENCE           │
                    │                                     │
                    │ Research • News • Insights          │
                    │ Recommendations • Risk Analysis     │
                    │ Portfolio Intelligence • Alerts      │
                    │ Natural Language Interface           │
                    └──────────────────┬──────────────────┘
                                       │
                              Read / Analyze
                                       │
                                       ▼
┌──────────────────────────────────────────────────────────────────┐
│                    DETERMINISTIC TRADING ENGINE                  │
│                                                                  │
│ Market Data → Order Validation → Risk → Order Book → Matching   │
│                         → Trades → Positions → Ledger            │
│                                                                  │
│              LOW LATENCY • DETERMINISTIC • AUDITABLE             │
└──────────────────────────────────────────────────────────────────┘

The agentic layer must never be allowed to compromise the correctness or latency of the core trading engine.

2. Core Design Principle
The most important architectural decision is to separate the platform into two planes.
Trading Plane
The trading plane handles:
Market data ingestion, order validation, margin checks, order books, matching, partial fills, positions, P&L, charges, settlement, MIS square-off and ledger updates.
This plane must be deterministic.
Given the same:
Initial State
+
Market Events
+
User Commands
+
Configuration

it should always produce the same:
Orders
+
Trades
+
Positions
+
Ledger
+
P&L
+
Events

Intelligence Plane
The intelligence plane handles:
Research
News
Market interpretation
Portfolio analysis
Screening
Recommendations
Risk explanations
Alerts
Natural-language queries
What-if analysis
Agentic workflows

This plane can be slower because it is not responsible for executing the actual matching algorithm.

4. Why the Agent Must Not Be Inside the Trading Engine
An LLM or autonomous agent should never be placed between:
Market Tick
     ↓
Order Book
     ↓
Matching Engine
     ↓
Trade

That would introduce unpredictable latency and nondeterministic behavior.
For example, if a market order arrives while the market is moving:
09:30:00.001   Market tick
09:30:00.002   Order arrives
09:30:00.003   Risk check
09:30:00.004   Matching
09:30:00.005   Fill

The matching engine should not wait for an AI model.
Instead:
                        ┌───────────────┐
Market Data ────────────►│ Trading Engine│──────────► Trade
                         └───────┬───────┘
                                 │
                                 │ Events
                                 ▼
                         ┌───────────────┐
                         │ Agentic Layer │
                         └───────────────┘
                                 │
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
             Research        Analysis       Recommendation

The agent reacts to the system.
The system does not wait for the agent.

5. Agentic Layer Responsibilities
The agentic layer can contain multiple specialized agents instead of one giant agent.
The recommended architecture is:
                      Agent Orchestrator
                              │
                 ┌────────────┼────────────┐
                 │            │            │
                 ▼            ▼            ▼
           Research       Portfolio      Market
             Agent          Agent        Analyst
                 │            │            │
                 └────────────┼────────────┘
                              │
                              ▼
                       Risk / Decision
                          Agent
                              │
                              ▼
                       Recommendation

The orchestrator decides which specialist should handle a task.
For example:
User:
“Why did my portfolio fall today?”
The orchestrator can execute:
Portfolio Agent
      ↓
Read today's P&L
      ↓
Identify largest contributors
      ↓
Market Agent
      ↓
Analyze price movements
      ↓
News Agent
      ↓
Search relevant company/sector news
      ↓
Risk Agent
      ↓
Analyze concentration/exposure
      ↓
Explanation Agent
      ↓
Generate final explanation

10. Agentic Screening
The Screener Agent can turn natural language into structured screening queries.
For example:
“Find liquid stocks that have fallen significantly but are showing increasing volume.”
The agent converts that into something like:
Universe:
NSE Equities

Filters:

Liquidity > X

Price decline > Y%

Volume change > Z%

Market cap > A

Data period = B

Then the deterministic analytics engine performs the actual calculation.
This is important.
The LLM should interpret the request.
The quantitative engine should calculate the numbers.
Natural Language
       ↓

       ↓

       ↓

       ↓

       ↓

       ↓

11. What-If / Simulation Agent
This is one of the strongest features you can add.
A user could ask:
“What happens to my portfolio if Reliance falls 8%?”
or:
“What if I buy 500 shares?”
or:
“What will my margin utilization look like?”
The agent should create a hypothetical scenario.
User Question
      ↓
Agent
      ↓
Scenario Builder
      ↓
Simulation Engine
      ↓
Position / Margin / P&L Calculation
      ↓
Result
      ↓
Agent Explanation

Critically, the simulation should use the same financial calculation components as the real engine wherever possible.
Do not create separate formulas for the agent.

A write operation must follow:

  ↓

  ↓

  ↓

14. Agent Safety Architecture
The agentic layer should have its own policy system.

    A["Agent"] --> I["Action Intent"]

    I --> P["Policy Engine"]

    P --> C{"Allowed?"}

    C -->|No| D["Reject + Explain"]
    C -->|Yes| R["Risk Engine"]

    R --> M{"Margin / Risk OK?"}

    M -->|No| X["Reject"]
    M -->|Yes| H{"Approval Required?"}

    H -->|Yes| U["User Approval"]

    U --> API

    API --> MATCH["Matching Engine"]

Policies could include:

Maximum position size
Maximum daily loss
Maximum leverage
Allowed instruments
Allowed order types
Maximum number of orders
Human approval requirement
Trading hours
Agent permissions

24. Financial Ledger
Every financial movement should create a ledger entry.
Conceptually:
Trade
  ↓
Charges Calculation
  ↓
Ledger Entries

For example:
BUY ₹100,000
Brokerage ₹20
STT ₹X
Exchange Charges ₹Y
GST ₹Z
Stamp Duty ₹A
--------------------------------
Total Cash Impact

Never simply update:
balance -= total

without recording why.
Instead:
LedgerEntry {
    id
    timestamp
    account_id
    reference_type
    reference_id
    debit
    credit
    amount
    component
    description
}

Then the balance can always be reconciled.

29. MIS Square-Off
The scheduled square-off is part of the deterministic trading plane.
At 15:20:
Scheduler
   ↓
MIS Square-off Job
   ↓
Get all open MIS positions
   ↓
Generate closing orders
   ↓
Risk validation
   ↓
Matching Engine
   ↓
Trades
   ↓
Charges
   ↓
Position = 0
   ↓
Ledger

Do not delegate this to an AI agent.
An agent may explain:
“Your MIS position will be squared off at 15:20.”
But the actual square-off must be deterministic.

41. Things the Agent Should NOT Do
The agent should never independently:
Modify ledger balances
Modify positions
Change executed trade prices
Bypass margin checks
Bypass order validation
Directly mutate database state
Override exchange rules
Change charges
Change matching logic
Force a trade
Invent market data
Invent research sources

All authoritative financial state belongs to the deterministic engine.

49. The One-Line Architecture Pitch
The strongest way to explain the project to judges is:
“We built a deterministic exchange simulator as the source of truth, and placed an event-driven agentic intelligence layer on top of it that can research, monitor, reason, simulate and recommend without ever compromising the low-latency trading path.”
That distinction makes the architecture much stronger than simply adding an LLM chatbot to a trading application.
